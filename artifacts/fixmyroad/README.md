# FixMyRoad

FixMyRoad is a civic-tech demo for reporting potholes and tracking municipal repair work. It includes a citizen report flow, AI-assisted image assessment, report tracking, and an officer dashboard.

## Run locally

From the workspace root:

```sh
pnpm install
pnpm --filter @workspace/fixmyroad run dev
```

The API runs as a separate workflow:

```sh
pnpm --filter @workspace/api-server run dev
```

The app expects `OPENAI_API_KEY` as a Replit Secret for real photo analysis. For local development outside Replit, copy `.env.example` to `.env` and add your own key there; never commit `.env`.

## Included features

- Responsive overview, report form, My Reports, Officer Dashboard, and How It Works pages.
- Browser-local demo reports and sample data, with demo-role switching instead of production authentication.
- Server-side image assessment through the OpenAI API. The key is read only by the API server and is never sent to the browser.
- Officer review, severity edits, assignments, notes, status history, and explicit confirmation before resolving.
- Citizen ticket details and status timeline.

## Demo data and limitations

Reports and uploaded report photos are saved in this browser's local storage. They persist across refreshes and are shared between the citizen and officer views in this browser, but they are **not shared across devices, browsers, or users**. The sample reports are labeled as demo data. The role switcher is not authentication, and this build is not a production municipal system.

AI assessments are decision support only. They do not verify road safety or prove that repair work was completed. If analysis is unavailable or uncertain, a citizen can submit the report for manual officer review.

## Data storage and production setup

This MVP does not write reports to PostgreSQL or upload photos to App Storage. That avoids exposing officer actions or user photos through a shared unauthenticated demo. A production deployment should add authentication and role-based authorization before enabling shared report records and persistent photo storage.

A suitable PostgreSQL design would use:

- `reports`: ticket ID, photo object path, location, description, AI assessment fields, severity, status, assigned team, notes, and created/updated timestamps.
- `report_status_history`: report ID, status, timestamp, and the authorized officer who made the change.
- `report_photos`: report ID, object path, photo purpose (`before` or `after`), and timestamp.

Store image bytes in App Storage, not PostgreSQL. Apply schema migrations only after defining the identity and authorization model for citizens and municipal officers.

## API

`POST /api/analysis/potholes` accepts a JPEG, PNG, or WebP data URL and returns a validated assessment:

```json
{
  "is_pothole": true,
  "severity": "medium",
  "confidence": 0.86,
  "reason": "A visible road-surface depression is present.",
  "needs_manual_review": false
}
```

The result is generated by the configured vision model; it is never replaced with a fabricated fallback. The endpoint has an image-size limit and a basic per-IP request limit.

## Configuration

Keep the key in Replit Secrets as `OPENAI_API_KEY`. The `.env.example` file contains only a placeholder. Never put the key in frontend code or commit it.

## Deployment

Publish the React web artifact and ensure the API Server workflow is included with it. Configure `OPENAI_API_KEY` as a production Replit Secret before enabling AI analysis. Until authentication and shared database storage are added, keep the app labeled as a local demo.
